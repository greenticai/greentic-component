# PR-04 — greentic-component — docs/examples only, no manifest break

## Goal

Keep `greentic-component` aligned with the newer flow-mapping terminology **without** introducing any manifest, ABI, runtime, wizard, or flow-regeneration change that would force existing components to update.

This PR should stay intentionally small and documentation-focused.

---

## Why this repo should not carry core mapping changes

`greentic-component` owns component authoring, manifests, scaffolds, and local tooling. The mapping model itself belongs to the **flow/runtime layer**, not to the guest component contract.

The current code already reflects that split:

- flow mapping lives in the `greentic-types` flow model
- component/runtime boundary notes live in `greentic-interfaces`

If we push mapping semantics into component manifests or `describe()` here, users may infer that every component must expose or implement those maps directly, which is not the goal.

---

## Important compatibility constraint

This PR must be **100% backward compatible**:

- no existing `component.manifest.json` becomes invalid
- no generated manifest shape becomes stricter
- no `describe()` payload shape changes
- no `flow update`, `build`, `wizard`, or runtime behavior changes
- no new required fields in manifests, schemas, or templates

If an idea requires any of the above, it does **not** belong in this PR.

---

## Scope of this PR

### Do

- update component-facing docs to explain that component schemas are the sources/targets that flow mappings shape around
- clarify that mapping is applied by the host/flow layer around component invocation
- align examples with the current canonical ownership split already documented in `greentic-types` and `greentic-interfaces`
- optionally add a tiny example snippet that shows conceptual flow mapping around a component call
- prefer the canonical `input` / `output` wording when describing current flow structure, while noting `in_map` / `out_map` / `err_map` only as flow-layer terminology or accepted aliases where relevant

### Do not

- add mandatory manifest fields for `in_map`, `out_map`, or `err_map`
- alter `describe()` output shape
- alter manifest generation behavior
- change `dev_flows` generation format
- change CLI flags or wizard answer schema
- introduce new dependency requirements for downstream repos

---

## Good documentation angle

Explain that a component provides:

- input schema
- output schema
- config schema

And the flow/runtime layer may use those schemas to:

- shape inputs before invocation
- normalize successful outputs after invocation
- normalize errors after invocation

Keep the separation explicit:

- component = capability + schemas + operation behavior
- flow/runtime = orchestration + envelope construction + mapping

---

## Best files to touch

- `README.md`
- `docs/component-developer-guide.md`
- `docs/cli.md` only if wording needs a small clarification
- optional: `docs/README.md` if it needs a pointer to the clarified flow/component split

Avoid changing code, schemas, snapshots, fixtures, or generated outputs unless a documentation test requires a tiny text update.

## Example snippet guidance

If a flow example is added, present it as **host/flow-side pseudocode** rather than a component manifest field.

Prefer something like:

```yaml
nodes:
  summarize:
    component: ai.greentic.summarizer
    input:
      mapping:
        text: payload.ticket.description
        system_prompt: config.summary_prompt
    output:
      mapping:
        summary: output.summary
    err_map:
      mapping:
        error_message: error.message
```

Then explain:

- the component itself does not declare these flow-node mapping fields in its manifest
- the host/flow layer applies them around the component call
- `in_map` / `out_map` remain acceptable flow-layer aliases, but component docs should not present them as new component-manifest fields
